# Choosing a structured-outputs backend: when GRID, when the default

You run a serving stack — vLLM today; SGLang and llama.cpp are next on the
[integration list](integrations-plan.md) — and structured outputs are on.
This document tells you which grammar backend to run. We build GRID, so we
argue for it where it has earned it, and we name the two cases where you
should run something else instead.

All numbers: the full JSONSchemaBench corpus (11,306 real-world schemas), one
machine, current versions (GRID 0.4.0, llguidance 1.7.6, XGrammar 0.2.3),
identical runner semantics. Per-schema statuses are committed
([`bench/RESULTS-jsonschemabench-v0.4.0.md`](../bench/RESULTS-jsonschemabench-v0.4.0.md)).

## The 30-second version

- **Schemas reach you from people you can't test in advance** — users,
  tenants, tool definitions from MCP servers and OpenAPI generators? **Run
  GRID.** You are not choosing a median compile time; you are choosing what
  the worst schema of the month does to your service. GRID's worst case is a
  named decline or a named re-validation list. It is never a silent lie.
- **Your schemas are a small, fixed, reviewed set?** Keep the stack default
  (XGrammar in vLLM). Its coverage is the widest, and on a fixed set you can
  test your way past its failure modes before they reach production. GRID
  buys you little here.
- **Compile latency is the budget** — schemas that are new on every request,
  sub-millisecond time-to-first-token? **Run llguidance.** Its lazy lexer is
  the compile-latency reference point. Nobody else is close, including us.

The rest of this document is the argument.

## The latency tables will not make this decision for you

Every backend comparison leads with per-token mask latency, so let's dispose
of it. Per-token medians for all three engines are 10–26 µs. A decode step on
an H100 is ~6 ms. At the median, masking is under half a percent of the step
for every engine on this page; measured end to end, GRID adds **+1.51% TPOT
at batch 32** against unconstrained decoding (H100 record at kernel v7,
[`bench/RESULTS-serving.md`](../bench/RESULTS-serving.md)). If two engines
differ by 15 µs at p50, your users cannot tell. Median mask speed is a solved
problem industry-wide, and choosing a backend on it is choosing on noise.

Two latency numbers *do* differ enough to matter, and we'll be plain about
both:

- **Compile time.** llguidance averages 0.6 ms per schema; GRID averages
  61 ms (p50 6.9 ms, p99 1.14 s); XGrammar averages 362 ms with a 5 s p99 -
  GRID is faster than the default on every compile percentile. If schemas are novel per-request and TTFT is your SLO,
  this row alone picks llguidance — that is its home turf and we say so.
- **Cold-mask tails.** GRID's first visit to a parser state pays a trie walk
  (bounded, ~8 ms p99.9); a write-back cache amortizes it across requests,
  so it is a first-request cost, not a steady-state one. The benchmark runs
  every schema once — serving does not.

Everything else that differs between these engines is not latency. It is
**what happens when a schema does something the engine didn't expect** — and
unlike latency, failure behavior doesn't average out. One bad schema is not
diluted by ten thousand good ones; it pages you.

## The real decision: four ways a schema can fail, ranked by pain

Here is the uncomfortable truth about running a platform: **you do not choose
your schemas — your users do.** You cannot know in advance how much of your
traffic is tidy tool-call JSON, how much is a 400-line draft-07 monster with
nested `anyOf`s, and how much is machine-generated by an agent that read the
spec differently than you did. So rank engines by their failure modes, worst
schema first:

1. **Compile never returns.** A worker wedged on one tenant's pathological
   schema. This is an outage.
2. **Valid output rejected mid-generation.** The schema is right, the model's
   output would have been right, the engine kills the stream. Your user files
   "structured outputs are broken" and you cannot reproduce it.
3. **Invalid output accepted silently.** The response violates the schema and
   nothing anywhere says so. This is a data bug discovered weeks later, in
   someone else's system.
4. **Compile declines with a named reason.** A log line and a fallback path.
   This is Tuesday.

Now the corpus, mapped onto exactly those modes (counts are schemas):

| what a bad schema does | GRID 0.4.0 | llguidance 1.7.6 | XGrammar 0.2.3 |
|---|---:|---:|---:|
| passes all instance tests | 10,159 (89.9%) | 9,487 (83.9%) | 10,212 (90.3%) |
| declines up front, named reason | 637 | 1,797 | 51 |
| rejects valid output mid-stream | **3** | 22 | 427 |
| accepts invalid output | 507 — **every one names its unenforced constraints** | **0** | 627 — **all silent** |
| never terminates | 0 — by construction (budgets) | 0 | 0 |

Read it with the ranking in mind:

- **Mode 2 is the row that decides for a platform.** XGrammar rejects valid
  output on 427 schemas of this corpus; GRID on 3. If your schemas are
  user-supplied, mode 2 is not a tail risk — it's a standing stream of
  support tickets with no reproduction path. This is the single strongest
  reason we can give you to switch off the default, and it is measured, not
  argued.
- **Mode 3: GRID is better on both counts that matter.** Fewer affected
  schemas than the default (507 vs 627) — and unlike the default's, none of
  them are silent: every GRID response carries the *names* of the
  constraints it accepted but could not enforce (`oneOf-exclusivity`,
  `uniqueItems`, …), so your pipeline re-validates exactly those,
  mechanically. A named gap is an engineering task; a silent gap is an
  incident. llguidance's 0 is real and principled — it refuses instead —
  which brings us to:
- **Mode 4: llguidance declines 16% of this corpus.** Principled, safe, and
  it means your fallback path (unconstrained generation plus a retry loop?)
  runs on one request in six. Be honest about whether that fallback is
  actually better than a masked generation with a named residue. In our
  experience it is not, and it is certainly less observable.
- **Mode 1: all three engines finish this corpus.** The difference is *why*.
  GRID's termination is not an empirical observation about a fast machine —
  construction budgets fire at input-derived points, so a pathological schema
  becomes a declared decline, deterministically, with the same outcome on
  your laptop, your CI, and your smallest prod node. You inherit the
  guarantee from the design, not from the benchmark.

## Function calling: the same argument, with execution attached

Tool calling is what most structured-output traffic *is* now, and it raises
the stakes on every failure mode above, for one reason: **tool arguments
execute.** A free-form response that violates its schema sits in a database
looking wrong; a tool argument that slipped past enforcement becomes the
query that runs, the API call that fires, the file that gets written. And
tool schemas are the least curated schemas in your stack — written by tool
authors, exported from OpenAPI, served by third-party MCP servers, sometimes
generated by another model.

The corpus contains three function-calling splits — 2,795 schemas, a quarter
of the benchmark
([derivation](../bench/RESULTS-jsonschemabench-v0.4.0.md)):

| split (schemas) | outcome | GRID 0.4.0 | llguidance 1.7.6 | XGrammar 0.2.3 |
|---|---|---:|---:|---:|
| BFCL (1,043) — curated, leaderboard-style | passing | 1,043 | 1,043 | 1,043 |
| Glaiveai2K (1,707) — real-world assistant tool calls | passing | 1,658 | 1,639 | 1,655 |
| | valid call rejected | **0** | 0 | 26 |
| | invalid args accepted | 18 — named | 0 | 26 — silent |
| | tool unavailable (declined) | 31 | 68 | 0 |
| MCPspec (45) — MCP tool specifications | passing | 42 | 35 | 41 |
| | valid call rejected | **0** | 0 | 4 |
| | invalid args accepted | 1 — named | 0 | 0 |
| | tool unavailable (declined) | 2 | 10 | 0 |

Three conclusions we'll stand behind:

- **On the curated split, all three engines are perfect.** 1,043/1,043
  across the board. If a backend pitch cites a leaderboard-style
  function-calling benchmark, it has told you nothing — that goes for ours
  too. The engines only separate on schemas from the wild.
- **On real-world tool schemas, the default's two failure modes both show
  up.** On Glaiveai2K, XGrammar rejects valid tool calls on 26 schemas —
  mid-call, which an agent loop experiences as a broken tool it retries at
  your token expense — and silently under-enforces arguments on 26 more.
  GRID rejected **zero** valid calls across all 2,795 tool schemas, and its
  19 partially-enforced tools are named, so you can gate dispatch on
  exactly them. llguidance never lies and never over-rejects — it makes 78
  tools unavailable instead (1 in 25 on Glaiveai2K, 10 of 45 MCP specs). On
  a tool registry, a decline isn't a log line; it's a capability your agent
  no longer has.
- **The fix for the residue is one `if` statement.** Compile at tool
  *registration* time, not call time, and gate dispatch on the recorded set:

  ```python
  src, recorded = compile_json_schema(tool.parameters)   # at registration
  # ... decode constrained by src ...
  if recorded:                                           # e.g. {"format"}
      validate(args, tool.parameters, only=recorded)     # before dispatch
  dispatch(tool, args)
  ```

  `strict=True` at registration moves the decision earlier still: a tool
  whose schema can't be fully enforced is rejected at onboarding, not at
  the 2 a.m. call. No other engine can offer this dial, because it requires
  knowing what wasn't enforced.

Mechanically, tool dispatch is friendly territory for the mask: tool names
are `const`/`enum` (enforced — a hallucinated tool name is unreachable, in
any engine that compiled the schema), and a multi-tool `oneOf` whose
branches carry distinct `name` constants is provably disjoint, so GRID
enforces the exclusivity rather than recording it. Function-call formats
are also the most boilerplate-rigid workload measured — 8–13% forced tokens
on the BFCL-style splits vs ~2% corpus-wide
([`bench/RESULTS-jf-density.md`](../bench/RESULTS-jf-density.md)) — which is
exactly what the jump-forward API targets; it stays default-off until its
serving measurement lands, per this repo's rule that machinery is measured
before it is advertised.

## Pick GRID when any of these is true

**1. You serve schemas you don't control.** Multi-tenant platforms, public
APIs, agent frameworks ingesting third-party tool definitions. This is the
headline case and the failure-mode table is the whole argument: 3
valid-rejections, no silent gaps, no non-termination, on the widest
uncurated corpus available.

**2. Your models call tools.** The section above, in one line: tool
arguments execute, tool schemas are the wild west, and GRID is the engine
that rejected zero valid tool calls while naming every argument constraint
it couldn't enforce — so you can gate dispatch on the residue instead of
trusting it away.

**3. Your output types are declared before the request is ever sent.**
Typed-pipeline frameworks — DSPy signatures, Instructor-style pydantic
extractors, fixed extraction templates — know at build time that
`sentiment` is one of three literals and `confidence` is a number. Compile
each signature once, and the framework's parse-retry machinery goes quiet:
an enum output cannot arrive misspelled, capitalized, or wrapped in an
apology. This is also the workload where GRID's cost profile inverts —
few schemas × many calls means compile once (the artifact store reloads it
across redeploys), then every call runs the warm path (25 µs p50). And
`strict=True` at program build time turns "this signature isn't fully
enforceable" into a CI failure instead of a production surprise.

**4. You need to know what was NOT enforced.** Every engine has constraints
it cannot express in a token mask. The defaults either refuse the schema or
accept silently. GRID returns, per compiled schema, the names of the
constraints it accepted but could not enforce (`recorded`), so
post-validation checks exactly those and nothing else. In regulated or
audited pipelines this is the difference between "we re-validate everything,
twice, forever" and "we re-validate the named residue." If you want the
refusal contract instead, `strict=True` turns every record into a hard error
— llguidance's convention, per request or per tenant. If a keyword you
depend on must be mask-enforced today, not recorded, the per-keyword matrix
is public: [`grid/jsonschema/SUPPORT.md`](../grid/jsonschema/SUPPORT.md).

**5. You're constraining a language, not a shape.** Text-to-SQL, query
builders, DSLs, config formats. JSON Schema is GRID's front end; underneath
is a general CFG engine, and SQL was its first customer. On our cross-engine
SQL harness (declared runner, protocol in
[`bench/RESULTS.md`](../bench/RESULTS.md)) GRID's warm mask p50 is 3.6 µs
with p90 80 µs, ahead of XGrammar's EBNF path (72 µs / 7.5 ms) — while
llguidance holds the better p99 (352 µs vs 5.3 ms) and XGrammar the faster
grammar compile; the corners are in the report. A grammar-shaped workload is
also where the layer above the mask becomes available: role-projected
grammars and the audit chain ([`beyond-the-mask.md`](beyond-the-mask.md)).

**6. A wedged worker is not an acceptable failure mode.** Pathological
schemas hit deterministic construction budgets and come back as declared
declines in bounded time — same schema, same outcome, on any machine. No
wall-clock racing, no "it compiled on staging but hangs on the small prod
box."

**7. Your deployment redeploys.** With the artifact store enabled,
previously-seen schemas reload instead of recompiling: warm-hit medians of
~17–23 ms for schema families whose cold compiles are seconds
([`bench/perfbench/BAKEOFF.md`](../bench/perfbench/BAKEOFF.md)). The store
never fakes a first compile — cold start on genuinely new schemas is
unchanged.

And one case that is not about serving at all: if you need **decode-time
RBAC, a replayable audit trail, or compliance-grade provenance**, no mask
engine attempts that layer. That case has its own document:
[`beyond-the-mask.md`](beyond-the-mask.md).

## Pick something else when

- **Your schema set is small, fixed, and tested.** Run the default
  (XGrammar): on a fixed set, both of its failure modes are discoverable by
  testing before deploy. Switching backends would be motion without benefit.
- **Novel schemas per request, TTFT-critical.** Run llguidance and accept the
  16% declare-rate with a fallback you've actually tested. Its 0.7 ms average
  compile is the number we openly chase; until our compile tail closes the
  rest of the gap, latency-dominated churn is its territory.
- **Your traffic is mostly regex constraints.** GRID's request surface is
  JSON Schema and `.grid` context-free grammars (SQL shipped first); there
  is no regex front end today. The incumbents cover regex and we don't yet.

## Running GRID under vLLM today

```bash
pip install "grid-guardrail[kernel]"          # engine + Rust kernels (5 platforms)
python bench/vllm_grid_patch.py               # vLLM 0.24.x: registers backend "grid"
                                              # (idempotent patch; upstream RFC in flight)
```

```python
from vllm import LLM, SamplingParams
from vllm.sampling_params import StructuredOutputsParams
from grid.jsonschema import compile_json_schema

source, recorded = compile_json_schema(schema)    # recorded = what to re-validate

llm = LLM(model, structured_outputs_config={"backend": "grid"})
out = llm.generate(prompt, SamplingParams(
    structured_outputs=StructuredOutputsParams(grammar=source)))

if recorded:                                      # e.g. {"oneOf-exclusivity"}
    revalidate(out, schema, only=recorded)        # your validator, scoped to the residue
```

Operational dials, in the order you'll reach for them:

- **`strict=True`** at compile time — refuse instead of record, per request,
  per tenant, or per registered tool. Use it where a named residue is not
  acceptable.
- **Artifact store** (`grid/serving/artifact_store.py`, default off) — warm
  redeploys; enable once you've seen your compile mix.
- **What to log:** compile declines (they carry reasons) and `recorded`
  names per schema. Those two streams are your early-warning system — they
  tell you what your users are actually sending before it becomes a ticket.
